# Standing Constraints

> **Role:** What still binds — the decisions and non-obvious facts that constrain future work, grouped by topic.
> **Read before any decision that might conflict with past work.**
> **Relates to:** receives decisions displaced from `progress-tracker.md` and decisions promoted out of `build-journal.md` at phase checkpoints.

## How this file is maintained

Keep this file **small**. It is the one record read on demand during ordinary
work, so every line costs on every session that opens it. The chronological
record of how the build got here lives in `build-journal.md`; this file holds
only what is still true.

- **Grouped by topic** (auth, data, payments…), never by date. Add a `##` topic heading when a new one is needed.
- **Holds only what still binds:** decisions that constrain future work, and notes explaining why something non-obvious is the way it is. Never a narrative of what happened — that is the journal's job.
- **Two things feed it,** and both are moves, never copies: the oldest bullet of `progress-tracker.md` → Key Decisions when that section would exceed 10, and each phase's still-binding decisions promoted out of `build-journal.md` at the phase checkpoint.
- **Cite the feature each bullet came from,** e.g. `(F02)`.
- **Deduped on write.** If a new constraint supersedes one already here, replace that bullet in place rather than adding a second bullet on the same topic.
- **Never pruned by age.** Remove a constraint only when it is verifiably dead — reversed by a later decision, or the thing it describes no longer exists. `git` history holds anything removed.

## Auth

- **`DISABLE_SIGNUP` is global, and must stay off.** Supabase's "Allow new users to sign up" toggle sits beside the email provider in the dashboard, but it governs every provider — turning it off stops new **Google** users from creating an account, which is the opposite of what this product needs. There is no per-provider email-signup switch: the only email control is the provider itself, and disabling that kills `signInWithPassword` and F03's isolation suite with it. (F04)
- **The open `/auth/v1/signup` endpoint is bounded, not closed, and the bound is `mailer_autoconfirm = false`.** A stranger can create an unconfirmed `auth.users` row (and a junk `profiles` row through the trigger), but no session is issued until the address is confirmed, so nothing reaches `/api/chat`. If autoconfirm is ever switched on, that becomes a real JWT-minting hole — which is why `tests/auth/auth-config.test.ts` asserts the flag directly rather than trusting the memory of this decision. (F04)
- **Google's authorized redirect URI is Supabase's, not the app's.** `https://<ref>.supabase.co/auth/v1/callback` goes in the Google Cloud console; `/auth/callback` is only where Supabase forwards the browser afterwards. Entering the app's URL yields `redirect_uri_mismatch`. (F04)
- **Every redirect is built from `SITE_URL`, never from the request's origin.** Render terminates TLS at a proxy, so `new URL(request.url).origin` inside a route handler can be the internal address. Supabase's own example works around this with an `x-forwarded-host` dance; using the configured site URL avoids the class of bug entirely. (F04)
- **`src/proxy.ts` refreshes cookies and never authorises.** Route protection lives in `(app)/layout.tsx` and in each route handler, independently. Nothing may be inserted between `createServerClient` and `await supabase.auth.getUser()` in the proxy — that call is what rotates the token. (F04)

## Database access

- **`public.handle_new_user()` is the one sanctioned `security definer` function in this codebase.** `library-docs.md` forbids `security definer` without a written reason; this is that reason. The function is fired by an insert on `auth.users`, executes as the auth admin role, and must write into `public.profiles` — there is no invoker-rights formulation that can do this, because the inserting role has no rights on `public`. It is written defensively for a reason Supabase states outright: **a trigger that raises blocks signup.** Hence `set search_path = ''` with every name fully qualified, a `coalesce` chain over the Google identity's metadata keys, and `on conflict (id) do nothing`. `execute` is revoked from `public`, `anon`, and `authenticated`. Any *further* `security definer` function needs its own entry here. (F02)
- **`createServiceRoleClient()` may be constructed only in `src/server/quota.ts`, and only for `shared_key_budget`.** A secret key assumes `service_role` and can read every row of every table, including other people's conversations and the ciphertext of their keys, so its blast radius is kept to one module. The two budget functions are `security invoker` with execute revoked from `authenticated` and granted to `service_role` — invoker rights plus a privileged caller, which is what keeps `handle_new_user()` the only `security definer` function here. (F17)
- **`bytea` is a hex string over PostgREST, and getting it wrong fails silently in the worst place.** There is no binary type in JSON, so `bytea` renders as `\x…` and `src/types/database.ts` types `ciphertext`, `iv` and `auth_tag` as `string`. Handing supabase-js a `Buffer` does not throw — it stores `{"type":"Buffer","data":[…]}`, reports success, and surfaces only when something later tries to decrypt a real user's key. The conversion lives in exactly one module, `src/server/data/provider-keys.ts`; everything above it speaks `Buffer`. (F13)
- **`shared_key_budget` gets no RLS policy — not in F03, not ever.** RLS is enabled and no policy is defined for any role, which makes the table unreachable through the anon key by construction rather than by rule. It is a global counter with no owner, so there is no `auth.uid()` to scope a policy to. The Supabase advisor reports `rls_enabled_no_policy` against it permanently; that notice is correct and must not be "fixed". (F02)
- **Extensions are created `with schema extensions`.** A bare `create extension pg_net` registers into `public` and trips the linter's `extension_in_public`. `pg_cron` is the exception — Supabase places it in `pg_catalog` and it publishes through its own `cron` schema. (F02)

- **Every RLS policy uses `(select auth.uid())` and is scoped `to authenticated`.** The bare `auth.uid()` is volatile to the planner and re-evaluated once per row; the subquery form is cached as an InitPlan. The role clause stops owner policies applying to `anon`, where they would overlap the share policies on `conversations` and `messages` and force Postgres to OR them per row. Both mistakes are functionally correct and quietly slow, which is why they are rules rather than judgement calls. The linter names them `auth_rls_initplan` and `multiple_permissive_policies`. (F03)
- **Two tables deviate from the uniform owner shape, on purpose.** `profiles` has no insert policy (the `security definer` trigger creates the row) and no delete policy (deleting it orphans the user against a surviving `auth.users` row that will never fire the trigger again). `shared_key_usage` has no delete policy — dropping that row is precisely how a user would reset their own daily allowance. Both are narrowings; do not "restore consistency" by adding the missing commands. (F03)
- **An owner can read their own `provider_keys.ciphertext`, `iv`, and `auth_tag` through PostgREST.** RLS is row-level, not column-level. Accepted, not overlooked: it is the user's own key material and is undecryptable without `ENCRYPTION_KEY`, which never leaves the server. A column-level `revoke` would close it but break `getDecryptedKey()` (F13), which must use the user-scoped client because the service-role client is reserved for `quota.ts`. (F03)
- **A write that RLS filters out looks exactly like a successful no-op, so a mutation that needs to report "nothing matched" must return a row count.** `deleteConversation()` and `setGeneratedTitle()` both `.select()` after the write and return a boolean; the route turns false into 404. One round trip where a read-then-write precheck would be two, and the condition stays inside the statement so the database decides once. (F10, F11)
- **`listConversations()` selects four columns, not `*`.** No CDN sits in front of the origin, and `system_prompt` can be 10,000 characters the sidebar has no use for. (F06)
- **The `attachments` bucket is private and stays private.** Storage paths must begin with the owner's user id, because the object policies match on the first path segment and nothing else — a path built any other way is unreachable by its own owner. (F03)

## Secrets and keys

- **The vault reads `serverEnv.ENCRYPTION_KEY` and validates nothing.** `env.ts` owns the 32-byte check and proves it at boot; re-checking in `vault.ts` would put one rule in two modules with nothing keeping them in step. `architecture.md` originally carried both spellings as invariants and the snippet resolved it the wrong way — narrowed to describe *use* rather than *read*. (F12)
- **`src/server/vault.ts` does not log. Not an error, not a provider name, not a length, not temporarily while debugging.** Everything it touches is either the master key or a plaintext provider key, and a log line is a response body written to disk. `DecryptionError` carries no `cause` for the same reason: `cause` is the field that ends up in a log by accident. Callers log instead — they hold the user id and provider, neither of which is secret. (F12)
- **A key probe distinguishes "your key is wrong" from "we could not find out", and both fail closed.** `401`/`403` → `400 invalid_key`; timeout, 5xx or network error → `503 probe_unavailable`. Neither writes a row. Collapsing them tells someone their correct key is invalid because a provider had a bad minute. Bounded by `KEY_PROBE_TIMEOUT_MS` (10s), not `STREAM_TIMEOUT_MS`. (F13)
- **The probe proves a key is real and authorised, not that inference is enabled.** It is a free models-endpoint call, so it spends nothing — and F14 did not close the gap, because it gave a key a place to be *used* rather than a second place to be checked. The gap surfaces as a failed first message carrying the provider's own reason. (F13, restated F14)

## Shell and layout

- **Shell layout state is a cookie, never `localStorage`.** `(app)/layout.tsx` is a Server Component, so it can read a cookie during render and emit the collapsed markup in the first byte. `localStorage` is unreadable until after hydration, which would paint the sidebar expanded and snap it shut on every navigation — for exactly the people who chose to close it. Read with `await cookies()`, written with one line of `document.cookie`; no route handler, because the server only reads it back. Names and values are in `src/lib/constants.ts`. **A cookie the server reads to decide a *query* must be followed by `router.refresh()`** — the collapse cookies do not, because React state already mirrors them and their server re-render is cosmetic, but F22's show-archived cookie chooses which rows `listConversations()` returns, so without the refresh the control flips and the list keeps answering the previous question. It also has to be read *before* the query is started rather than beside it. (F05, extended F22)
- **Sheet motion is entry-only. Never add a closing animation.** Radix defers unmounting a closing element to an `animationend` whenever the computed `animation-name` changes on close. When that event does not arrive, the overlay unmounts while the panel stays on top of the page, visible and interactive — observed directly, with Escape leaving the sidebar stranded at `data-state="closed"` and no animation running. With no exit keyframe the name stays `none` and Radix unmounts at once. A CSS transition is not a substitute: Radix listens for `animationend`, never `transitionend`. (F05)
- **The sidebar reaches `AppShell` as a rendered Server Component node, not as an imported component.** That is what keeps its markup in the RSC payload instead of the client bundle, which matters because no CDN sits in front of the origin. The consequence to remember: it cannot receive callbacks, so the collapse toggles read state through React context instead. **`OutlineRail` is the deliberate exception** — its content is derived from `useChat` state that exists only in the browser, so there is no server markup to preserve and the rule has nothing to protect. It is still slotted rather than imported, so the arrangement is unchanged from `AppShell`'s side. (F05, narrowed F18)
- **The outline rail and the thread are siblings, and the channel between them is `AppShell`.** `OutlineRail` is slotted in by the `(app)` layout while the messages live in `Chat` inside `children`, so no prop reaches from one to the other. `AppShell` holds the outline state; `Chat` publishes `{entries, activeId, jumpTo}` and the rail reads it. That is what makes "derived from the already-loaded thread, no extra query" literally true. Two rules keep it stable: the publish effect **must clear on unmount** (without it the previous conversation's rail follows the user onto `/settings` — reproduced by removing it), and the entries array **must be memoised on content**, not on `messages`, which gets a new identity per streamed token. Measured: 1 publish per response with the memo, 14 without. Keyed on `id:label` rather than ids alone, because F19 edits a prompt in place. (F18)
- **A message may carry a hand-written `id`; nothing inside a shell column may.** The no-id rule exists because below 1024px a column is in the document twice — the `display:none` desktop aside and the mounted sheet. The thread is not: `children` renders once in `AppShell`. So message anchors are ids (`outlineAnchorId`, spelled in one place) and rail items use `aria-current`. Measured with the sheet open at 800px: two rail lists in the DOM, zero duplicate ids document-wide. (F06, extended F18)
- **The outline's active entry is decided by position, never by crossings.** "The last anchor to cross the reading line" is correct scrolling down and wrong scrolling up — scrolling back past a prompt leaves it as the most recent crossing while the reader is above it. `IntersectionObserver` reports both `isIntersecting` and `boundingClientRect`, and recording where an anchor *is* is direction-independent. Any future change here must be walked in **both** directions. (F18)
- **The mobile drawer traps focus into the sidebar, and it lands on the first row's overflow trigger.** Measured: with the drawer open, `document.activeElement` is `BUTTON[Options for …]` and the first `<li>` matches `:focus-within` with no user action at all. Any `group-focus-within:` rule on a sidebar row therefore fires for free whenever the drawer opens — which is how F11's timestamp ended up hidden on touch. Worth re-checking at F37 whether the trigger is the right thing to receive that focus. (F11)
- **Radix dismisses a Sheet from `document.addEventListener('keydown', …, { capture: true })`**, which runs before the root listener React attaches — so `stopPropagation()` inside a React handler cannot stop the drawer closing, and the first version of F21's rename cancel took the whole sidebar with it at 360px. A `window` capture listener is one step higher in the path and sees the key first. Read out of `@radix-ui/react-use-escape-keydown`, not inferred. (F21)
- **A Radix menu traps focus until it has finished closing.** Anything the menu reveals must be focused from `onCloseAutoFocus` (with `preventDefault()` to stop focus returning to the trigger), never from an effect keyed on the state change: the effect runs while the scope is still trapped, and the measured result was a rendered input with `document.activeElement` on `BODY`. (F21)
- **React fires no blur for an element it unmounts.** A ref flag that a blur handler is supposed to clear must *also* be cleared where the interaction starts — F21's cancelled rename left `cancelledRef` set forever, and the next rename on that row silently discarded its own blur commit. (F21)
- **A sidebar row is `<li class="group">` with the link as a sibling of the overflow trigger**, because a button cannot live inside an anchor. Two consequences: `group-focus-visible` does not work once focus can land on a descendant (use `group-focus-within`), and the link needs `after:absolute after:inset-0` to keep the whole row clickable, with the trigger lifted above it by `relative z-10`. (F11)
- **The timestamp and the overflow trigger share one grid cell**, swapping rather than each taking a slot, so the title's truncation point never moves. On a coarse pointer the container becomes a flex row and both show — grid placement is inert on a flex item, so the same two children serve both modes. The timestamp carries `pointer-events-none`: inline text paints above a non-positioned sibling's box, so it otherwise wins the hit test and swallows clicks meant for the trigger. (F11)
- **No element in the sidebar list may carry a hand-written `id`.** Below 1024px the desktop `<aside>` is `display:none` but still in the document while the drawer copy is mounted, so every id would exist twice. Group headings use `<ul aria-label>`, never `aria-labelledby`. Radix's generated ids are safe — `useId` derives from tree position, and the two copies were measured producing different values with zero duplicates document-wide. (F06, confirmed F11)
- **The layout starts the conversation query and hands the sidebar an unawaited promise.** Nothing under `src/components/` may import from `src/server/`, and awaiting in the layout would block the whole frame on a database round trip and make the skeleton dead code. The sidebar awaits it inside `Suspense`. (F06)
- **Sidebar day groups are UTC calendar days**, consistent with `shared_key_usage.usage_date` and needing no timezone cookie. Accepted cost: near midnight a user far from UTC sees a heading that disagrees with the row's own relative time. (F06)
- **A collapsed column leaves a 36px gutter strip holding its restore button.** Not in `DESIGN.md`, which says only that the columns collapse. A fully hidden column has no way back, and a floating restore button would overlap the thread once F09 fills it. (F05)
- **The 404 lives at `app/not-found.tsx`, at the root, and cannot be moved inside the shell.** Next resolves a path matching no route against the root not-found; a `(app)/not-found.tsx` fires only for an explicit `notFound()` inside a route that already exists. Anything else would mean a catch-all route existing purely to fake it. (F05)

## Testing

- **There is no local Supabase stack.** Migrations are authored as files under `supabase/migrations/` — still the source of truth — and delivered to the hosted project through the Supabase MCP. Consequences that bind everything downstream: no `supabase db reset`, so no migration is ever proven replayable from zero; types come from MCP `generate_typescript_types`, not `gen types --local`; and F03's RLS suite runs against the cloud instance. (F02)
- **`playwright-cli open` is headless unless given `--headed`.** The tell is inside the page: `screen.width` reads exactly 1280×720 headless and the real display size otherwise. F10 lost several minutes hunting for a window that was never drawn, and asked the user to find it too. The binary is also called "Google Chrome for Testing", not "Chromium", which is what someone scanning their dock is looking for. A second gotcha found at F11: two sessions cannot share one `--profile` directory, because Chromium locks it — close the first before opening the second. (F10, extended F11)
- **The browser tool is the `playwright-cli` skill.** The Playwright MCP server was removed and replaced by it; `CLAUDE.md` and `library-docs.md` pointed at the dead MCP for a while, which is how F06 came to record its whole visual pass as *Not verified* — the extension was not connected, the MCP was gone, and the skill that was available the entire time went unchecked. Check the skill list before concluding a browser is out of reach. It is a debugging tool only: `@playwright/test`, `playwright.config.ts`, and `e2e/` still arrive at F36. Sign-in is Google OAuth, so open with `--persistent --profile` or `state-load` a saved session. (F06)
- **Component behaviour has no automated coverage, and will not until F36.** `vitest.config.ts` matches `tests/**/*.test.ts` only — no `.tsx`, no jsdom, no React Testing Library — and Playwright arrives at F36. Anything UI-shaped is verified in a browser and recorded as such; the testable residue is pure helpers, which is why F05 extracted `resolveDisplayName()` and `initialOf()` into `src/lib/utils.ts` rather than inlining them. Do not report a UI feature as "tested" on the strength of `pnpm test`. (F05)
- **Unit tests live in `tests/`, and `server-only` is aliased to an empty stub under Vitest** — otherwise every `src/server/` module throws at import time, before a single assertion runs, for a reason unrelated to what is being tested. The stub must stay empty; the real guard still does its job at build time. (F01)
- **Data and policy tests run against the hosted project and own their fixtures.** There is no local stack and no `seed.sql`. The pattern, established in `tests/rls/isolation.test.ts` and to be reused by every later data test: `auth.admin.createUser({ email_confirm: true })` on the service-role client with a `crypto.randomUUID()` email, then `signInWithPassword` on a publishable-key client to get a real JWT, then assertions through that client. `afterAll` deletes the users and the cascade clears the rest. (F03)
- **Seed fixtures with the service-role client, never through the policies under test.** If seeding goes through a policy that is broken, the table ends up empty and every "cannot see the other user's row" assertion passes for entirely the wrong reason. (F03)
- **Delete storage objects before deleting an auth user.** Supabase refuses to delete a user who still owns objects, and reports it as a generic delete failure that looks nothing like the cause. (F03)
- **Vitest ships in Phase 0, Playwright at F36.** F03's RLS suite needs the former; nothing needs browser binaries until there is a spec to run. (F01)
- **Turbopack does not reliably hot-reload a route handler.** Two rounds of "the fix does not work" at F08 were a stale module, with zero diagnostic output from code that was definitely on disk. Restart `pnpm dev` before believing a server-side change had no effect. (F08)
- **Assert on a condition, never on a fixed `waitForTimeout`.** Two "bugs" at F07 were premature reads taken before a `router.refresh()` round trip completed; the database already held every row, in order. Relatedly, an opacity read in the same tick as a keypress returns the *start* of a 150ms transition. (F06, F07)
- **Driving Radix from the console does not work.** A programmatic `element.click()` will not open a menu — the trigger listens on `pointerdown`. Use a real click, and disambiguate the duplicated sidebar with Playwright's `:visible`. (F11)
- **`PGRST303 'JWT issued at future'` on the first load after sign-in is clock skew, not a code fault.** Transient disagreement between GoTrue and PostgREST at the moment the token is minted; a reload clears it. Seen at F07 and again at F10. (F07)
- **To prove a prompt reached the provider, make it change an answer.** A column holding the right string proves storage, not delivery. F23 set the system prompt to "always reply with exactly the word BANANA" and asked for the capital of France; the override guard was proven the same way, by a crafted `fetch` carrying that prompt against an existing conversation and getting Tokyo. Two shared-key messages, and the only check that answers the question actually being asked. (F23)
- **Verify on the surface the code writes to, not the one that shows the outcome.** F19 found three defects this way — a `.catch()` that could never run, a dropped per-call body, and a flaky tie test — and every one of them left the screen looking perfect while the database disagreed, usually only after a reload. F29 was caught by the same rule from the other direction: the chips, the progress bar and the send all behaved while every file was quietly uploading twice. When a change writes to the database, read the database. (F19, restated F29)
- **A verification pass that only exercises the case the code was written for is a demonstration, not a test.** F18's outline marker was walked in both scroll directions because the rule it implements is only obviously correct in one of them, and going up is where it was wrong. The same move is what proved F28's guards: the thing to do with a new guard is give it something to refuse. (F18, restated F28)
- **A test suite that has never failed proves nothing.** The RLS suite was verified by weakening a policy to `using (true)`, confirming exactly the two expected tests went red, and restoring it. Any future change to these policies should be checked the same way. Phase 2 made this the standing habit and it earned its keep every time: it exposed a test comparing a function against itself (F15), a test swallowing its own assertion inside its own `catch` (F12), and a concurrency test that could not fail at all (F16). **The mutation that breaks a test is rarely the one you predict** — deleting `setAuthTag` left all three tamper tests green and broke the round-trip ones instead. (F03, hardened F12–F17)
- **`shared_key_budget` is a singleton row shared by the whole project, not a fixture.** With no local stack, a suite that writes it is writing the ledger the running application reads — so `tests/server/budget.test.ts` snapshots the row in `beforeAll` and restores it in `afterAll`. Without that, one run leaves the shared key genuinely tripped for everyone. **And snapshot/restore is not sufficient, which has now happened rather than being predicted:** a network fault killed the suite between the two at F19, leaving `estimated_usd = 11.0000` and `tripped_at` set on the live project until it was repaired by hand. The mutation and its undo are not atomic, so any abort in between disables the shared key for real users. Treat a test that writes this row as an outage risk, not a fixture. (F17, hardened F19)
- **A hosted-project suite must tear down with `Promise.allSettled`, never `Promise.all`.** One rejected delete under `all` discards the other's outcome and silently leaves a fixture user on a project that has no reset. Observed at F19. Only `edit-message.test.ts` has been changed; the others still use `all`. (F19)
- **`tests/security/key-exposure.test.ts` greps `src/app` for identifiers and cannot tell a comment from a call.** Mentioning `getDecryptedKey` in a route's doc comment fails it. The bluntness is correct for a secrets guard — comments bend around it, never the other way round. (F17 checkpoint)
- **A suite that reaches `src/server/` needs its Supabase seam mocked, or it dies at import.** Anything pulling in `createServerSupabaseClient` reaches `cookies()`, which throws outside a request scope. Use `vi.doMock` + `vi.resetModules()` + dynamic import, or `vi.mock` with `importOriginal` when only one export needs replacing. Modules reaching the database *only* through the service-role client have no such problem and can be imported and called directly. (F14, extended F17)

## Quota and limits

- **The two quota limits are `NEXT_PUBLIC_*`, and the prefix is load-bearing.** Next inlines only that prefix into client bundles, and the composer displays the daily cap — unprefixed, the UI would fall back to its default while the server enforced the configured number, and the two would disagree silently with nothing to indicate it. Neither value is a secret. The cost is that both are inlined at build time, so changing either on Render needs a rebuild rather than a restart. (F01)
- **`reconcile_shared_key_usage()` shipped early, in F02 rather than F17**, because F02 registers the `cron.schedule` call that invokes it and a job pointing at a missing function fails every ten minutes. It is `security invoker`: pg_cron runs it as the table owner, which bypasses RLS without needing elevation. **A scheduled job is not verified by its exit status.** This one had run every ten minutes since 2026-07-31 with an unbroken wall of green in `cron.job_run_details` — 866 runs — and had never once corrected anything, because there were no reservations to correct until F16 and no orphan ever after. It is verified by giving it something to fix and watching it fix that: the four tests added at the Phase 2 checkpoint watch it zero a stale counter, leave a fresh one alone, decline to *raise* a counter when a delivered message outran the reservation, and retire a `streaming` row abandoned mid-stream. Both guards were then priced by mutation — removing the staleness clause zeroed a *live* reservation, and removing `message_count > actual` billed a user for a generation the reserve path had already missed. (F02, tested at the Phase 2 checkpoint)
- **Title generation reaches the shared key through `sharedTitleModel()`, never `resolveModel()`.** No longer a precaution: `resolveModel()` now calls `reserveSharedSlot()`, so routing titling through it would charge every user a daily message for a title they never asked for. `sharedTitleModel()` takes no user id, so there is nobody to charge; one test pins its arity at zero and another asserts it never reads a stored key. (F10, enforced from F16)
- **Titling spend goes to `shared_key_budget` and only there, and the sweep can never cover for a missed call.** `reconcile_shared_key_usage()` derives usage from `messages` rows carrying `used_shared_key`, and a title writes no message row, so those tokens are invisible to it by construction. `recordSharedBudgetTokens()` takes no user id, which is what makes "accounted, never charged" structural rather than remembered. (F10, closed at F17)
- **A daily slot is claimed, never checked.** `reserve_shared_slot` is a *single* SQL statement whose `where message_count < p_limit` sits on the `do update` branch. A read followed by a write — in any form, including inside one transaction — reopens the race. **This is held by the implementation's shape and not by the suite, which was established by proving the test cannot fail here:** replacing the upsert with the exact read-then-write it forbids left the concurrency test green, and so did widening the window to a full second with `pg_sleep` between the read and the write. Requests to the hosted project serialise — ten calls each sleeping a second took eleven — so no second statement ever lands inside the window, through a signed-in client, a header-only client, or a raw `fetch` alike. The invariant is confirmed against the live database with `pg_get_functiondef` rather than against the migration file. Proving atomicity needs a local stack or F36; until then, any change to this function is verified by reading the deployed definition. (F16)
- **`estimated_usd` is derived from the cumulative token totals, never accumulated per call.** Measured: one title-sized call is $0.00051 and stores as $0.0005 in `numeric(10,4)`, so per-call accumulation drifts downward ~2%, and a mutation swapping derive for accumulate turns exactly that test red with exactly those figures. The structural reason outlives the arithmetic and is the half that generalises: an accumulated dollar column is a second independent record of a fact the token columns already hold, free to disagree with them forever with nothing to notice — the same shape as F12's two-places validation and F15's two spellings of one rule. Derive from the exact thing; never keep a rounded copy beside it. (F17)
- **The breaker check is scoped to the current `period_month`, and dropping that term is a deadlock.** A breaker tripped in one month would refuse in the next, and the reset that clears it lives on a write path the refusal itself blocks. Unrecoverable without manual SQL, reachable by doing nothing. (F17)
- **The breaker is checked inside `reserveSharedSlot()`, before the claim.** Not at the call site, so no path can spend a daily message to buy a user a 503. (F17)
- **`isSharedKeyAvailable()` fails open, deliberately.** The authoritative spend cap is the hard budget limit on the Google billing account (F38), not this application. Failing closed would trade a real outage for a few hypothetical cents. The in-app breaker is best-effort by design, which is also why the ledger records measured usage only and never an estimate. (F17)

## Chat and streaming

- **`POST /api/chat` owns conversation creation; `conversationId` is nullable and null means "create one".** A separate endpoint would put creation on the far side of the refusal path, so every F16 quota wall and F17 tripped breaker would strand an empty "New chat" in the sidebar. One handler owning both is what keeps "a refusal leaves no trace" true. (F07)
- **Nothing is persisted until the request is certain to reach a provider**, and the route carries an explicit marker where that line sits. The ordering is easy to violate by accident and invisible in review once violated. Feature 19 raised the stakes rather than changing the rule: an edit **deletes** every message after the one it rewrites, so the same line that used to prevent a dangling prompt now prevents a destroyed conversation. Measured — moving the truncation above `resolveModel()` returned the *identical* 429 and took a six-message thread to three. Anything destructive added later belongs below that marker with everything else. (F07, hardened F19)
- **`editMessageId` lives on `chatRequestSchema`, and edit-and-resend has no endpoint of its own.** A `PATCH /api/messages/[id]` would put the delete on the far side of the refusal path — truncate succeeds, the send is then refused on quota, and the thread is gone with nothing to restore it from. Same argument that put conversation creation in this handler at F07. (F19)
- **The thread's order is `(created_at, id)`, in both `listByConversation()` and `edit_message_and_truncate`.** `created_at` alone is not total, and "every message after this one" needs an exact meaning before anything can delete by it. The tiebreaker is arbitrary but *consistent*, which is the whole requirement: truncation and display agree, so a reply can never survive beneath a prompt that no longer produced it. Excluding the target by id instead — the first attempt — deletes an *earlier* tied row. These two are halves of one rule; changing either alone breaks it. (F19)
- **`edit_message_and_truncate` is a database function because PostgREST cannot span a transaction.** Update-then-delete as two round trips can fail in the middle and leave an edited prompt followed by the answer to the question it used to be. It is `security invoker`; RLS is what scopes it, and it returns null — not an error — when the target is missing, not the caller's, or not a user message, because those three must stay indistinguishable. (F19)
- **A message's client id and its database id diverge unless something puts them back.** A thread seeded from the server carries real uuids; a message `useChat` has just streamed carries an id the SDK minted, and `router.refresh()` does *not* resync them — only a real navigation does, which is why the divergence is invisible on a new conversation (`router.replace()` remounts `Chat`) and live on an existing one. Two mechanisms close it, and **both are load-bearing** — each was removed in turn and broke a different case:
  - **The server reports the row a prompt became**, as a transient `data-prompt-message` part alongside F08's `data-conversation`, and the client adopts it in `onFinish` (never mid-stream — rewriting an id changes a React key). Without it, editing a message *sent in the same session* sends an SDK id and 400s.
  - **`editMessage` uses `sendMessage`'s own `messageId` option**, which replaces a user message in place keeping its id and truncates after it. Without it the SDK pushes a *new* invented id while the database updates the original row, so the *second* edit of one prompt 400s.

  The general rule outlives both: **before a request body names a row, ask which side minted the id.** Only server-minted ids may name server state. Where a row can be described instead — F20's regeneration says "the last answer" and sends no id at all — that is stronger still, but only for non-destructive targets: a position that drifts silently destroys the wrong thing, whereas a stale id fails loudly. (F19, fixed at F20)
- **A regeneration is refused unless the conversation's last row is an assistant message**, because that is the only thing it can replace. The client sends `regenerate: true` and no id at all — see above. (F20)
- **`chatRequestSchema` is a union whose branches are `.strict()`, and strict is the load-bearing half.** `z.union` tries members in order and a plain zod object strips undeclared keys, so a body carrying both `message` and `regenerate` would match the send branch, lose the flag, and be handled as an ordinary send — appending a prompt the thread already holds. Any new branch added here is strict too. (F20)
- **`useChat`'s `sendMessage` does not reject.** `makeRequest` catches, calls `onError`, and sets `status: 'error'`. Anything that has to undo optimistic client state on a refusal must watch `status`, never `.catch()` — which compiles, reads correctly, and never runs. (F19)
- **`prepareSendMessagesRequest` must spread the `body` argument it is handed.** It builds the request body, so a per-call `sendMessage(msg, { body })` override is silently dropped unless spread in. The failure is quiet in the worst way: the request is simply an ordinary send, so the client's optimistic view and the database diverge and only disagree after a reload. (F19)
- **AI SDK v7, read off the installed `.d.ts` rather than the docs.** `onFinish` is a deprecated alias for `onEnd`. `onAbort` receives only `steps`, and a single-step generation stopped mid-flight has none — a partial answer must be accumulated in `onChunk` and written from both `onAbort` and `onError`. Compose the abort signal with `request.signal`, or the stop button hides a response the provider keeps billing for. (F08)
- **`touchConversation()` is load-bearing, not bookkeeping.** There is no trigger on `conversations.updated_at` and the sidebar orders on it; skip it and the list silently stops reflecting activity. (F07)
- **`router.refresh()` is what reflects a mutation, not `revalidatePath()`.** The sidebar query lives in the `(app)` layout, which Next preserves across navigation. Every route here reads cookies and is therefore dynamic, so there is no Full Route Cache entry to invalidate — tested at F11 with a controlled A/B on back-navigation, with and without, behaving identically. (F07, confirmed F11)
- **PostgREST cannot span a transaction.** A conversation can outlive the message that justified it, so the chat handler deletes a conversation it just created if the message insert throws. (F07)
- **The model catalog is an enforcement boundary, checked in `resolveModel()` and nowhere else.** An id absent from `src/lib/models.ts` is `UnknownModelError` → `400 unknown_model`. Deliberately not also in `chatRequestSchema`: one rule in two files is two rules free to drift. The check runs *before* the key lookup, so an unknown model costs no round trip and never brings a plaintext key into existence — proven load-bearing, since moving it below the key read turns exactly one test red. (F14)
- **A rule two runtimes both enforce gets one definition.** `isSharedModel`, `findModel`, `isModelAvailable` and `willUseSharedKey` in `src/lib/models.ts` are each called from both the browser and the server. Two spellings disagree invisibly in both directions — a picker offering a model every send then rejects, or hiding one that works. That each is genuinely load-bearing in *both* places is measured rather than assumed: inverting `isSharedModel` turns one test red in the picker's suite and one in the server's. Composing shared primitives is not the same thing as writing one rule twice — F20's regenerate menu reads the same two functions the composer does and states its own conclusion from them. (F15, F16)
- **Model selection is keyed on `(provider, modelId)`, never the id alone.** The same model appears under two providers with different ids and different bills. `decodeModelKey` splits on the **first** separator, because a model id may contain a colon (`:free`, `:thinking`) while a provider — a Postgres enum — cannot. (F15)
- **OpenRouter needs `compatibility: 'strict'` and `.chat(modelId)`.** The factory defaults to `'compatible'`, which omits `stream_options: { include_usage: true }`, so a streamed response reports no usage at all and every message persists with null tokens — which the breaker's ledger would read as "this cost nothing" rather than as missing data. The callable's first type overload also resolves to a *completion* model while the runtime dispatches to chat. (F14)
- **`SHARED_MODEL_ID` is pinned to a version, never an alias.** Google 404s `gemini-2.5-flash` for new users while still listing it from the models endpoint, so the catalog is not proof a model works — verify with a real call. The key is billed and F17 derives `estimated_usd` from a Flash rate card, so an alias that moves to differently-priced weights makes that ledger wrong silently. (F08)
- **A conversation is auto-titled only while its title is still `'New chat'`, and the gate sits above the provider call.** A repeat request therefore costs one indexed read and no money, and F21's manual rename is protected without a column to record it. F21 added the test that keeps the guard from being tidied away: remove the `.eq('title', …)` and a renamed conversation is silently re-titled by the model. (F10, tested F21)
- **"Listed" and "available" are different claims, and only one can be checked for free.** Every id in the catalog was read from a live endpoint *and then generated against*, because the endpoint is not evidence: Google still lists `gemini-2.5-flash` and answers a real request to it with "no longer available to new users". That id was run as a deliberate control and failed as predicted, which is the only reason the passes mean anything. The same pass killed a Pro tier — `gemini-3.1-pro-preview` is listed, is not on the shared key's free tier, and so is absent rather than shipped hopefully. For anything a provider publishes about itself, a catalog read is a hypothesis and a real call is the test. (F14)

- **A catalog that only feeds a picker is decoration; this one refuses, and refusing is what gives an empty catalog teeth.** `architecture.md` had said since F02 that `model_id` "must exist in the catalog in `src/lib/models.ts`" — a file that did not exist, guarding a column that accepted any string ≤120 chars. F14 made it real by checking membership in `resolveModel()` and **only** there: not in `chatRequestSchema` as well, because one rule in two files is two rules free to drift, which is exactly what F12 had to unpick in the vault. The check runs *before* the key lookup, since an unknown model cannot succeed and refusing first avoids a database round trip and a decrypt — a mutation moving it below `getDecryptedKey()` turned exactly one test red, which is how that ordering is known to be load-bearing rather than incidental. The consequence lands on `openai` and `anthropic`, which ship as **empty arrays** because no key existed to prove a single id for either: a user with a valid, stored, working OpenAI key still cannot send a message. That is not a bug to route around but the honest state of the product, so `UnknownModelError` builds its message from the catalog and says "PromptX has no OpenAI models available yet" rather than blaming a model id that was never wrong. F15's picker will show both groups empty, which is the right place for it to be visible. (F14)

- **Two things that looked like work and were measured to be none: a test that could not fail, and a fix that fixed nothing.** The availability test asserted `isModelAvailable(p, m, [])` against `isSharedModel(p, m)` — but with no configured providers the first *reduces* to the second, so it compared a function against itself and would have passed for any implementation. The mutation run is what exposed it: inverting `isSharedModel` left it green while turning its neighbours red. Rewritten to state the rule literally, it now catches. Separately, `<Chat key={conversation.id}>` was added to stop stale model state leaking across a conversation switch — and removing it changed nothing, because Next already remounts the segment on a param change. The first attempt to check that used a full page `goto`, which remounts everything and could never have told the difference; only a client-side sidebar navigation could. The line stays, with a comment saying it pins behaviour rather than fixes a bug. Both belong to one habit: after adding a test or a guard, break the thing it protects and confirm it notices. (F15)

## Conversation state

- **`PATCH /api/conversations/[id]` is one endpoint over a union of `.strict()` branches** — model, rename, pin, archive, system prompt — and any new intent is added as another strict branch. Same reason as `chatRequestSchema`: `z.union` tries members in order and a plain zod object strips undeclared keys, so a body carrying two intents would match the first and be answered as something nobody asked for. The route narrows with `in` and never an assertion, which is also why branch order is irrelevant to correctness. (F21–F23)
- **Four of those five writes deliberately leave `updated_at` alone** — rename, pin, archive and system prompt. The sidebar orders on *activity*, and naming, filing, pinning or instructing a conversation is not activity. It bites hardest on pin and archive, where a touch would reorder the row inside its own group for a click that produced no message. Only `touchConversation()` — a real send — may move it. Each is held by a test that goes red when `updated_at: now()` is added. (F15, F21–F23)
- **Every conversation write returns a boolean from `.select('id').maybeSingle()`, and the route turns false into a 404.** RLS makes someone else's row invisible rather than forbidden, so an update matching nothing reports no error and is otherwise indistinguishable from success. 404 rather than 403, because confirming that an id exists but is not yours is itself a disclosure. (F11, F15, F21–F23)
- **`Archived` is checked before `Pinned` in `labelFor()`, and archiving never clears `pinned_at`.** A row can be both — that is what lets unarchiving restore it to Pinned exactly as it was — so one has to win the grouping, and put-away beats lifted-up: a conversation the user filed should not reappear at the top of the sidebar the moment archived rows are revealed. (F22)
- **Empty, whitespace-only and null are one state**, for the title and the system prompt alike, collapsed in the schema with `.trim()` declared *before* the length checks (zod runs checks in declaration order — measured on 4.4.3). For the system prompt this is load-bearing beyond tidiness: null is what makes the chat route send `system: undefined`, where an empty string would be a *value* handed to the provider. (F21, F23)
- **A `systemPrompt` in a chat request body is honoured only when that request creates the conversation.** On `/chat` there is no row to have stored one, so the body is the only path it can arrive by; for an existing conversation the route reads the row and ignores the field. Honour it anywhere else and a standing instruction becomes a per-request override — one answer generated under rules the conversation does not record, with nothing on screen or in the database to say so. Nothing structural holds this: it is one branch in `/api/chat`. (F23)
- **`listConversations(includeArchived)` widens and never narrows.** The flag defaults to false, so hiding archived rows is what happens when nobody says otherwise, and a flag that filtered the wrong way round would hide *live* conversations — the one failure here that would look like data loss. (F22)

## Prompt library

- **`prompts` needed no migration, and `updated_at` is written by hand on every edit.** The table, its four owner policies and both indexes shipped in F02; what F02 did *not* give it is a trigger, so `updatePrompt()` sets the column itself. This is the one place the codebase deliberately departs from the rule four conversation writes follow — the sidebar orders conversations on *activity* and renaming one is not activity, while the prompt grid orders on `updated_at` because editing a prompt is the only activity a prompt has. Held by a test that goes red when the column is dropped from the statement. (F24)
- **Tag normalisation lives in `promptTagsSchema` and the order of its five lines is the schema.** Element checks run first (trim, lowercase, per-tag cap), then array checks in declaration order: `.overwrite()` dedupes, and only then does `.max()` count. `.overwrite()` rather than `.transform()` is what makes that possible at all — it preserves the schema type so `.max()` can still be chained. Reversed, eight identical tags are refused against a database that would have held one. The two array caps are not a duplicate: the first bounds what is *parsed*, the second is the product rule. (F24)
- **The library is read once per page session, cached in a module, and invalidated by `usePromptMutation`.** Component state would be discarded on every conversation switch, because `Chat` remounts per conversation — so "once per session" would quietly mean "once per conversation". Measured: exactly one `GET /api/prompts` across three opens and a switch. Without the invalidation, a prompt saved on `/prompts` is invisible to the composer's picker until a reload, which is the user's own change going missing. (F25)
- **Two different searches over prompts, deliberately.** `/prompts` matches titles only, because it has a row of tag chips beside its box; the composer's picker matches titles **and tags**, because it has no room for that row and a tag would otherwise be unreachable from the composer. Two rules, not two spellings of one — both pinned by tests in the same file so the divergence stays a decision. (F24, F25)
- **`prompts_tags_idx` is reported unused and that is now correct rather than pending.** Tag filtering happens in the browser over one server read, so nothing queries tags in SQL. Whether to drop it or to use it is a decision for whoever needs server-side tag filtering. (F24, F25)

## Attachments

- **Every Supabase Storage call lives in `src/server/data/attachments.ts`.** Mechanically, `eslint.config.mjs` restricts `CallExpression[callee.property.name='from']` outside `src/server/data/` and excludes only `Array`, `Buffer` and `Object` — so `supabase.storage.from(…)` trips it anywhere else. Substantively, an image is three objects and every deletion path has to take all three, which is only checkable by reading one module. (F28)
- **A row exists before its signed upload URL is issued, and `'ready'` is measured rather than claimed.** The order stops an object existing with nothing naming it — the only leak the reaper's *object* pass can reach. The confirm route reads each object's metadata back out of Storage and overwrites `size_bytes` and `mime_type` with what landed; a missing object is `409 upload_incomplete` and the row stays `pending` for the reaper. Without that, a client can mark an upload complete that never happened, spend a quota slot, and fail at the provider. (F28)
- **The bucket's `file_size_limit` and `allowed_mime_types` are the only thing enforcing size and mime**, because uploads go client-direct through signed URLs and the application is never in the byte path. Both figures are restated in SQL from `src/lib/constants.ts`, which is the one place they can drift, and `tests/server/attachments.test.ts` pins them together and uploads a real oversized file and a real SVG to confirm Storage refuses both. Any fixture that uploads to this bucket must use an allowed mime — F03's text blob went red the moment the limits existed. (F28)
- **`position` is assigned at link time from the order of `attachmentIds`, never carried on the draft**, and `link_attachments_to_message` repeats the ready-and-unlinked conditions inside its own `where` so the check and the write cannot be raced apart. It is a database function for F19's reason: PostgREST cannot span a transaction, and a message showing two of its four files is a state nothing downstream can repair. (F28)
- **`verify_jwt` is not authorisation for an Edge Function.** It checks only that a JWT was signed by this project, so every signed-in user satisfies it — for `reap-attachments`, which deletes things, that is no gate at all. It is disabled, and the function instead proves the caller holds a service-role key by reading `shared_key_budget`, the table F02 deliberately left without a policy for any role. That probe works for both `sb_secret_…` and the legacy JWT format, which a string comparison against one injected env var would not. (F28)
- **The reaper deletes objects first and rows second, in both passes, and batches by path count rather than row count.** A crash in between leaves a row pointing at a missing file, which the next run clears; the reverse leaks the file with nothing left to record it existed. `remove()` caps at 1,000 paths and an image is three, so a row batch is 333. Its TTL constant is duplicated from `src/lib/constants.ts` because Deno cannot import from the Next application, and a test reads the function's source to keep them equal. (F28)
- **The two Vault secrets are `reap_attachments_edge_url` and `reap_attachments_service_key`**, created outside the migrations because one of them is a service-role key and `supabase/migrations/` is committed. Until both existed, `reap_attachments_tick()` had run green and hourly since F02 while doing nothing at all. (F02, closed F28)

- **A `setState` updater must be pure, and StrictMode is the only thing that will tell you it is not.** F29 started uploads inside the updater that added the chip; development double-invocation made every attachment upload twice, create two rows and six objects, and leak one of them — with nothing visible on screen. Side effects belong in an effect, and that effect needs its own idempotency guard (a `started` set keyed by local id), because effects double-run too. The same audit caught `remove()` and `clear()` revoking object URLs and issuing DELETEs inside their updaters. (F29)
- **`sendMessage({ messageId })` is a replace primitive, not a way to name a new message.** Read off the installed SDK: it looks the id up, **throws** when it is not already in the thread, and truncates everything after it — right for F19's edit, wrong for anything else. To mint an id for a *new* message, pass a whole message object (`{ id, role, parts }`), which takes the branch that uses `id` as given. (F29)
- **The model is sent the `_inline` derivative, with its bytes inlined as a data URL.** No signed URL is ever handed to a provider: it is a bearer token for a user's private file and would sit in a third party's logs for its lifetime. Every turn that has attachments carries them, not just the newest — otherwise a follow-up about an image is answered confidently about nothing — and the accepted cost is that each image is re-billed per turn, which is also why it is the 1440px webp rather than the original. A history object that cannot be read is skipped with a warning; one on the *current* turn is fatal, because somebody is waiting for an answer about it. (F29)
- **Attachments reach the screen through a map keyed by message id, never through SDK message parts.** A message sent moments ago exists only in `useChat` state, where no server render can reach it and `router.refresh()` does not help. The map is seeded server-side, added to optimistically on send, and re-keyed when `data-prompt-message` reports the real row — in the same place `adoptPersistedPromptId()` re-keys the message, because they must move together or a just-sent image vanishes when the answer lands. (F29)
- **`status = 'failed'` is never written, deliberately.** A failed upload deletes its row and objects — `uploadAttachment` cleans up what it created, so a retry starts from nothing rather than stacking a second row — and the chip's failed state is local. The send path already refuses anything that is not `'ready'`, so a persisted status no code consults would be bookkeeping pretending to be a state machine. The check constraint keeps the value available. (F29)
- **Upload progress needs `XMLHttpRequest`; `fetch` cannot report it at all.** Progress is weighted across the original and both derivatives by bytes, not by object count — an original is often twenty times its thumb, so counting objects parks the bar at 66% for almost the whole wait. (F29)
- **`inline_width` / `inline_height` are the one client-reported thing on an attachment row**, bounded by `ATTACHMENT_INLINE_MAX_PX` in the schema, and exist only so `next/image` can carry explicit dimensions. Cosmetic by construction: a wrong value costs a layout wobble where a wrong `size_bytes` or `mime_type` would be a security claim, which is why those two are measured at confirm instead. Nothing else may start trusting them. (F29)

## Search

- **A search snippet is plain text and must never be rendered as HTML.** `ts_headline` does not escape the document it summarises — measured: `<script>` was stripped but `<img src=x onerror=alert(2)>` came through verbatim, and fragment selection cut another tag in half. Message content is model output and user input, so `search_messages` delimits matches with `chr(2)`/`chr(3)` (`SEARCH_MATCH_START`/`SEARCH_MATCH_END`) rather than `<mark>`, and the renderer splits on them into real React elements. This is what makes "only `<mark>` is permitted, never arbitrary HTML" a fact about the data rather than a rule. Anything that ever puts a snippet near `dangerouslySetInnerHTML` has reintroduced the bug. (F26)
- **`search_messages` takes no user id and must never take one.** It is `security invoker`; the owner policies are what scope it. Note the isolation is provided by **two** policies, not one: the inner join to `conversations` means a row needs both its message and its conversation visible, so weakening either alone changes nothing. Defence in depth, but it also means no test of this query can isolate the `messages` policy — measured, after a mutation to it left the whole suite green. (F26)
- **Zero results has two causes and they need different words.** A stopword-only query parses to an empty `tsquery` and could never have matched; `search_has_terms` distinguishes that from a real query that found nothing, and is asked only when the result set is empty. `searchMessages()` returns an outcome union rather than an array so the two cannot be collapsed by a caller. (F26)
- **The `/search` URL is the state, written with `router.replace` and never `push`.** Pushing each debounced keystroke turns Back into a walk through `d`, `de`, `dep`. **The input tracks outstanding navigations by count, not by comparing values** — two value-comparing designs were measured failing, the second because navigations land *out of order*: type `deploy`, keep typing to `deployment`, and the slower `deploy` render arrives carrying a query nothing remembers, looks external, and deletes four characters the user watched themselves type. Every landing this component caused consumes one outstanding navigation whatever it carries; only a change arriving at zero may touch the draft. A navigation that would change nothing is skipped against the *live* `window.location`, or the tally never comes back down. (F27, fixed at the Phase 4 checkpoint)
- **A search result deep-links with `?m=<uuid>`, consumed once.** `/chat/[id]` reads it and `Chat` runs F18's `jumpTo`, which brings the highlight with it; the param is then stripped with `router.replace` so a reload does not drag the reader back to a message they have scrolled away from. A hash was rejected because Next does not reliably scroll to a target that hydrates after a client-side transition — an effect is needed either way, and the hash arrives without the highlight. (F27)
- **Every message carries a scroll anchor, and both roles can be highlighted.** F18 built the anchors and the highlight for the outline rail, which lists prompts only, so `AssistantMessage` had neither until search started returning answers. The assistant highlight is a pseudo-element in the column's gutter, **never a real border**: DESIGN.md `message-assistant` says a response carries no fill and no border, and the first attempt — `border-l-2` plus `pl-lg` — indented every response by 18px against a spec line that calls it "full width of the message column". A pseudo-element occupies no layout, so nothing moves whether it shows or not. (F27, corrected at the Phase 4 checkpoint)
- **⌘K listens on `window` with `capture`.** Radix dismisses overlays from a `document`-level capture listener that runs before React's root listener, so anything hoping to see a key before a Radix layer must sit a step higher in the capture path. Verified reaching the app with a dialog open. It navigates rather than opening a palette, which would need a `GET /api/search` that does not exist. (F27)
- **The search order is `ts_rank desc, created_at desc, id desc`, and the tiebreakers are not decoration.** Rank collisions are ordinary — far more common than the `created_at` ties F19 had to make total — so without them the same query returns the same rows in a different order between calls. (F26)
- **`messages_search_idx` is not used at the current table size, and that is correct.** Measured over 5,001 rows with RLS active: the planner chooses a sequential scan for both a 20%-selectivity term and a one-row term, because the table is ~142 buffers. Forcing `enable_seqscan = off` picks `messages_user_id_idx`, still not the GIN. So no composite or `btree_gin` index was added — the evidence says the index that exists is not yet earning its keep, let alone a second one. Re-measure before adding one. (F26)

## Message rendering

- **Syntax highlighting runs in the browser and cannot run anywhere else.** The thread lives inside `Chat`, a Client Component holding `useChat` state, so a streaming message has no server render and after `router.refresh()` even persisted messages come from client state. What makes it affordable: shiki's JavaScript RegExp engine instead of ~1 MB of Oniguruma WASM, plus dynamic imports throughout. (F09)
- **The twelve-language allowlist is a *compatibility* guarantee, not a size one** — lazy loading already handles size. The JS engine cannot emulate every Oniguruma pattern and `forgiving` would swallow exactly that failure, so extending the list means extending the test that loads each grammar for real. Use shiki's canonical ids: `bash`/`sh`/`shell`/`zsh` are all aliases of `shellscript`. (F09)
- **Intercept a fence at `pre`, never at `code`.** Branching on `className` only sees a fence that named its language; a bare fence has no class, falls to the inline branch, and renders as inline code mid-paragraph. (F09)
- **Highlighting waits until a message settles.** Re-tokenising a growing string is quadratic over a stream, and a half-written fence tokenises as whatever it currently looks like. (F09)
- **Markdown renders for the assistant only.** Rendering a user message would silently reformat the person's own words and break the match between what is on screen and what the model was sent. Raw HTML stays off — model output is untrusted input. (F09)
- **A streaming error boundary must reset on content change.** Without it one bad fragment ends the message permanently as raw text; with it, the message recovers on the next delta. Measured both ways. (F09)

## Design system

- **`cn()` must declare every custom token scale.** `tailwind-merge` knows only Tailwind's default class groups, so it dropped `text-button-md` when composed with `text-on-primary` and failed to dedupe `rounded-sm` against `rounded-pill`. `src/lib/utils.ts` uses `extendTailwindMerge`; a token added to `globals.css` and not to that list is silently unreliable. (F01, extended F05)

- **Never use a named width utility.** The `DESIGN.md` spacing tokens shadow Tailwind's container scale, so `max-w-md` is 10px and `max-w-xs` is 4px — the shadowing is silent, with no error and just a collapsed element. Widths are numeric on the 4px grid (`max-w-112` = 448px), enforced by an ESLint rule. (F01, extended F05)

- **The `@theme` font tokens reference the `next/font` CSS variables, never the family names.** `next/font` emits two families per face — the real one and a metric-matched fallback with an ascent/descent override — and only the CSS variable names both, in order. Writing the literal `Inter` still finds the self-hosted face but skips the fallback and drops to `system-ui` while the webfont loads, which is the exact layout shift `next/font` exists to prevent. (F01)

- **shadcn primitives are retuned in place, with no alias layer.** `globals.css` carries only the PromptX `@theme`; the CLI's `:root`/`.dark`/`@theme inline` layer was deleted wholesale and each primitive hand-edited. One vocabulary, and a freshly added component looks visibly wrong until it is retuned — which is the intended forcing function, not an inconvenience to work around. (F01)

- **A `canvas-soft` container on a `canvas-soft` surface is invisible, and DESIGN.md specifies several.** The model picker's "Shared" marker and the composer's quota meter both drop their specified container and render as text alone — DESIGN.md's own "the container never changes colour, only the text does" survives intact, because there is no container. Check the parent surface before reaching for `status-chip`. (F15, F16)
- **A dialog a parent opens must be mounted only while open, never left mounted with an `open` prop.** Radix calls `onOpenChange` **only for changes it initiates** — a trigger, Escape, the overlay, the close button — and never when a parent flips the prop, so seeding fields in that handler runs on every close and on no open at all. `PromptDialog` shipped that way and reopened holding the previous prompt; saving wrote a byte-for-byte duplicate. Mounting per open makes `useState` initialisers do the seeding, so there is no event to forget. The remount is observable — `useId` returns a new value each time. (F24)
- **Anything that moves focus out of a closing Radix layer must yield through `onCloseAutoFocus`, conditionally.** Radix restores focus to the trigger *after* your own focus call, so inserting a prompt landed the text and caret correctly and left focus on the button. `preventDefault()` there lets your focus stand — but only on the path that has somewhere better to send it: Escape and click-outside must still return focus to the trigger, or a keyboard user who changes their mind is stranded on `<body>`. Insert, Escape and click-outside are three ways through one exit, and a fix has to be checked on each. (F25, and F21 before it)
- **A destructive confirmation is an `AlertDialog`, not a `Dialog`.** It carries `role="alertdialog"`, drops outside-click dismissal, and focuses Cancel rather than the button that destroys something. Its surface is a deliberate copy of `dialog.tsx` — two confirmation shapes that looked different would read as two systems. F13, F19, and F24 all reuse it. (F11)

- **Hide with `pointer-fine`; never rely on `pointer-coarse` to reveal something a hover rule hides.** Tailwind emits `group-focus-within:opacity-0` *after* `pointer-coarse:opacity-100` and both are single-class specificity, so the hiding rule wins. Default to visible and let only a fine pointer hide anything — a variant that fails to match then leaves a control reachable rather than stranded. A pair that both *reveal* (`opacity-0` + `group-hover:opacity-100` + `pointer-coarse:opacity-100`, as `MessageBubble` does) has no conflict and is fine as written. (F11)

## Tooling

- **`corepack` is not assumed to exist.** Node 26 does not ship it, so it cannot be assumed present on Render's build image either, and the failure mode is a build that dies with `pnpm: not found`. `pnpm` is installed via `npm`, and F38's build command reads the version out of `packageManager` to keep the pinning guarantee Corepack would have given. (F01)
