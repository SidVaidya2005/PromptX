# Progress Tracker

> **Role:** Live build status — what's done, in progress, and next.
> **Read at the start of every session**; **update after every completed feature.**
> **Relates to:** mirrors `build-plan.md` exactly; evicts old decisions to `constraints.md`.

Any AI agent reading this should immediately know what is done, what is in
progress, and what is next.

## How this file is maintained

- **Current Status is overwritten, never appended.** It holds three lines describing only the latest state. Do not keep previous statuses here — the record of what happened lives in `build-journal.md`.
- **Progress checkboxes are edited in place** — tick the box for the completed feature. Never restate, duplicate, or re-list the checklist.
- **Key Decisions holds the 10 most recent decisions, newest first.** When adding an 11th, file the oldest bullet under its topic in `constraints.md`, so this section never exceeds 10. Eviction is a move, never a delete — an old decision can still bind.

## Key Decisions

1. **Deploying is what found the four things planning could not, and two of them were assumptions this repo had carried for six phases.** The largest is that the shared key's free tier grants **20 requests a day across every user combined, not per user** — measured by a real 429 naming `generate_content_free_tier_requests, limit: 20`. The app had promised 20 per user, so the first visitor would consume the entire project's quota and everyone after them would be refused by *Google*, with a raw provider error, rather than by PromptX's own wall — leaving the quota meter, the composer's message and the link to `/settings/keys` as dead code in production. The cap is 5, and the fallback default in `constants.ts` moved with it because a default is what runs when configuration is missing and must under-promise. The same measurement retired §38's "not optional" budget cap: there is no billing account, and the replacement is stronger rather than weaker, since Google enforces the quota itself and refuses with a 429 instead of a charge. **The corollary is recorded rather than left to be inferred** — the monthly USD breaker now guards nothing, because `estimated_usd` derives from a rate card against spend that never happens, and it must never be cited as evidence spend is bounded. **Retrying a rate limit was the second finding and it cannot ever work**: the SDK fires three attempts at roughly 0s, 2s and 6s against a retry-after of 52s, so one refused request becomes three — 15% of a 20-request day — and the retries hold the bucket empty so the outage outlives the burst that caused it. Disabled on the shared path only, and priced by mutation. The third and fourth were documentation that had been wrong since Phase 0 and could not fail loudly: Render's build-filter keys are `paths`/`ignoredPaths` rather than `included`/`ignored`, and because a synced filter **replaces** rather than merges, our spelling would have emptied it and quietly resumed rebuilding on every doc commit; and every environment variable including the secrets is required at *build* time, because `env.ts` parses at module load and `next build` evaluates those modules — which is exactly how the first deploy died, reading like a code fault. **Two verifications became possible for the first time**: `/share/*` genuinely sends `private, no-store`, which dev had always misreported, and the hourly reaper genuinely reaches its Edge Function — the check that would have caught F28's 866 green-but-useless runs. **And two of my own claims were wrong**: an allowlist probe that a control proved could not fail — the authorize endpoint echoes any `redirect_to`, listed or not — and retry arithmetic that overstated the cost until the titling gate was actually read, which turned out to skip the provider entirely when a generation fails. Both were corrected on measurement, one of them only because it was questioned. (F38)

2. **An audit finds what the audit tool cannot see, and three of this feature's tests could not fail until they were broken on purpose.** Axe reported zero violations at every impact level across all nine routes — and still missed a real WCAG AA failure, because `--color-danger` is drawn on `canvas-soft` in the alert dialog and every in-dialog error, and none of those states is open during a route sweep. Computing every text token against every surface it can appear on caught it at 3.88:1. The same gap in reverse produced the other two findings: three components had re-implemented the focus ring as a box-shadow while deleting the global outline (two spellings of one rule, the F15 shape, and the box-shadow one carries a `ring-offset` colour that is wrong on any surface but canvas), and the landing page shipped 222.9 KB against a 200 KB budget because `supabase-js` sat at module scope for a page whose only interactive element is one button — deferring it to the click took it to 158.3 KB without changing what a visitor experiences, since the next thing that happens is a redirect to Google. **The tests that could not fail are the part worth carrying forward.** `toBeVisible()` ignores opacity entirely, so the coarse-pointer checks passed with the reveal rule deleted; `toHaveCSS('opacity','1')` on the control passed too, because the `opacity-0` lives on the wrapper; only multiplying opacity up the ancestor chain turned the mutation red. Separately the landing-JS check first measured **0.0 KB** — `next start` serves chunked and gzipped, so `content-length` is usually absent and the assertion summed nothing — and the scroll check reported zero long tasks without ever confirming the page had scrolled. Each was found by breaking the thing it claimed to protect, not by review. Two documentation corrections came with it: `next build` under Turbopack no longer prints First Load JS at all, so §37's instruction to review that output refers to a table that does not exist, and the "four specs and no more" rule was amended in writing rather than quietly exceeded. (F37)
3. **Two things a doc had asserted for six phases were simply not true, and the feature's real work was finding that out.** `library-docs.md` had said since Phase 0 that provider calls are intercepted with `page.route()`. They cannot be: `page.route()` sees browser requests and the browser never contacts a provider — `streamText` runs inside `/api/chat` and `probeKey` inside `/api/keys`, both server-side. The specs intercept the application's own routes instead, and the line was corrected rather than worked around. The second is subtler and would have produced a permanently green lie: **`route.fulfill()` sends the whole body at once**, so a canned "stream" arrives as one chunk and any assertion about incremental rendering passes identically against a blob. A real SSE server on an ephemeral port, reached with `route.continue({ url })`, is what makes the claim checkable — proven by collapsing three deltas into one and watching the test go red. **Three defects were then found in my own harness, all by measurement rather than review**: `globalSetup` runs *after* `webServer`, so the carefully-worded clean-checkout message arrived as a Next build stack trace until the preflight moved to config load; an intercepted mutation must also perform the write it pretends to do, because `router.refresh()` re-renders from the database rather than from the response; and the add-key display proved intermittent under interception. That last one was diagnosed instead of retried away, and the honest conclusion is narrower than the first guess — the write and the fulfilment succeeded every time, and the real un-intercepted DELETE path on the same page refreshed 4 runs out of 4, so it is an artefact of the row being written by the test process, recorded as a follow-up rather than announced as a product bug. **Sessions are minted by `@supabase/ssr` itself** against an in-memory cookie jar, so nothing here hand-encodes a cookie format that has already broken across minors once. (F36)
4. **A test suite made of assertions about things that exist cannot notice a thing that is missing — and the two structural bugs this feature found came from files sharing state, not from any one file being wrong.** F35's census exists for the first half: no behavioural test can fail because a policy has no test, so a separate check reads what the migrations declare and fails on any policy the grid does not name. It parses migrations rather than `pg_policies`, which PostgREST does not expose — reaching the catalog would mean a second `security definer` function against a constraint that names `handle_new_user()` as the only sanctioned one, and `architecture.md` already says the schema lives in migrations. The two were compared once through the MCP and agreed: 32 declared, 32 live. **The second half is what parallelism exposed.** `recordSharedKeyTokens()` forwards to `recordSharedBudgetTokens()`, so a new suite covering it mutated the global singleton — and because Vitest runs files in parallel it raced `budget.test.ts` however carefully each one restored, both going red at `expected 10814 to be 420`. Exactly one file may write that row. Minutes later the same shape again: F19's tie test pins `…001`/`…002` as message primary keys and the new suite pinned the same two, so the second insert hit a duplicate key — and it read as an ordering bug purely because the seed's error was unchecked. Deterministic ordering does not require constant ids; a shared random prefix differing in the final nibble gives both. **And a wrong diagnosis was corrected by repeating the mutation rather than by reasoning harder**: weakening `owner updates` to `using (true)` left the suite green, which looked like an assertion trusting the reply instead of the row — but after the fix it was *still* green, because Postgres applies SELECT policies to an UPDATE carrying a WHERE clause, so the write never selected a row. The update cell cannot isolate the UPDATE policy at all, which is the F26 shape, and the test now says so instead of implying otherwise. (F35)
5. **When a spec asks for a mechanism the codebase cannot honestly provide, implementing the word is worse than correcting it.** §34 asked for the export to be "streamed as a download". `listByConversation` does `select('*')`, so the whole thread is in memory before the handler can write a byte — a `ReadableStream` over that array would have satisfied the wording, read as compliance in every review afterwards, and delivered none of the benefit. That is the same decorative-mechanism failure F28 recorded for guards with nothing to refuse and F31 for a stop button that stops nothing, arriving a third time in a third costume. Real streaming needs a paginated read, which is a genuine follow-up rather than something to smuggle in, so the *build plan* changed instead of the code pretending. **The second decision is the one that would have leaked**: the JSON export picks every field by name, and that is a security property rather than a style preference. A spread of the row exports `user_id`, the token counts, and `share_slug` — a live public URL travelling inside a file people forward, which revoking the link afterwards cannot reach — and it would silently begin exporting any column added in a later feature. The test asserts against the *serialised* payload rather than field by field, because the thing it guards against is a field nobody thought to name; adding `...message` turned it red on the user id. And **a harness mistake produced a confident wrong answer before it produced a right one**: `pkill -f "next start"` kills the pnpm wrapper and not the `next-server` child, so a pre-F34 build kept the port, the new server died into an unread log with `EADDRINUSE`, and a route the build manifest plainly listed "404ed" for several minutes. What broke the deadlock was reading the *shape* of the failure rather than the status — `x-nextjs-prerender: 1` and `text/html` is a static not-found page, which is not what a handler refusing a request looks like. Kill by port, and when a route that exists returns 404, suspect the server before the code. (F34)
6. **A policy is scoped to a role, so "public" and "signed out" are not the same thing — and the gap between them is invisible until the wrong person opens the link.** F03's share policies are `for select to anon`, written a whole phase before anything rendered a shared conversation, and they are correct. What nobody had reason to notice is that Postgres applies a policy only when the *current role* matches, and Supabase resolves a signed-in JWT to `authenticated` — so reading a share link through the ordinary cookie-bound client returns **nothing** for any visitor who happens to be logged in. That is not an edge case; it is the common one, since a link is usually passed between two people who both use the product. Nothing errors: the query succeeds and comes back empty, and the page 404s as though the slug were wrong. Found by reading `pg_policies` while planning rather than by hitting it, which is the only cheap way it *could* have been found. The fix is a genuinely anonymous client, and the reason it is the fix rather than the alternative is worth keeping: **widening the policies to `to anon, authenticated` would have leaked far more than it solved**, because `listConversations()` deliberately carries no `user_id` filter — RLS is the boundary, not the query — so an `authenticated` policy of `using (share_slug is not null)` would put every shared conversation in the system into every user's sidebar. An isolation test now asserts the gap in both directions, so the next person to "simplify" this is told why it does not work. Two more from the same feature. **A test can pass every assertion and still be blind to the thing that matters**: the slug's uniqueness, length and character-set tests all stay green when `& 63` becomes `& 15`, which cuts the keyspace from 71 bits to 48 — only a test that samples which characters are actually emitted catches it, at `expected 16 to be greater than 60`. And **the dev server lies about `Cache-Control`**: it reports `no-cache, must-revalidate` where production sends the required `private, no-store`, so an invariant about caching verified in dev gives the wrong answer and invites a fix to something that was never broken. (F33)
7. **An invariant is a rule with a reason, and the honest move when a feature meets its edge is to name the exception and its cost — not to quietly break it, and not to let it veto the feature.** F32 had to write an assistant message the server never produced, because F31 persists nothing and the answer the user chose exists only in their browser. The rule it meets — history never comes from the request body — was written to stop a client steering a *completion* with a fabricated past, and the promote route calls no provider at all, so nothing about it can be steered. Two alternatives were available and both were worse: keeping every comparison server-side in memory (lost on deploy, broken by a second instance, and a "persists nothing" route quietly becoming stateful), or regenerating on promotion, which hands back a different answer than the one that was picked and defeats the feature it implements. So `architecture.md` names the route as its one exception and states the price in the same sentence — a crafted body can store a turn no model said, and F33 will publish it — with the corollary that any *other* route growing a field like this is a bug. **The second decision was the one that could have gone wrong silently**, and it is arithmetic rather than policy: the promoted row is written `used_shared_key: false` even though the shared key really did produce it, because F31 already counted that spend in `compare_count`. Marking it true counts one generation twice, and since the sweep only ever *lowers*, the raised floor blocks a legitimate refund on some *unrelated* orphaned slot later the same day — the user charged for a generation they never received, ten minutes after the fact. Nothing on screen would ever say so; the mutation is what says so, turning the new test red at `expected 2 to be 1`. Two smaller ones. **A `finally` block undoes a deliberate exception** — the promote hook leaves its pending flag true on success on purpose, so the button does not flash back for a frame before the navigation, which means every failing path has to clear it by hand and forgetting one leaves a permanently disabled button. And **the strongest verification was not a query but a question**: asking the promoted conversation "which of those three is the largest" and being told "the Blue Whale" proves the two rows are real history, which counting rows never could. (F32)
8. **A limit is only enforced where something can still see the evidence, and a feature that persists nothing is invisible to the job that reconciles it.** `reconcile_shared_key_usage()` has been correct since F02 for one reason nobody had to state: every spent shared-key slot left a `messages` row, so counting those rows and lowering `message_count` to match could only ever release orphans. F31's compare view spends the key twice per click and writes nothing at all — so **every slot it claimed would have come back within ten minutes**, and the daily cap would simply not have applied to `/compare`: two generations a click, unbounded, with only the global monthly breaker in the way. Nothing fails, nothing logs, and the only symptom is a counter that is lower later. It was found by reading the sweep during planning and asking what its source of truth actually was, which is the only way it *could* have been found; no test of the compare view would have noticed, because the sweep runs ten minutes after the test ends. The fix is a second counter moved inside the same atomic upsert that claims the slot, added to the sweep's `actual` — `message_count` stays the only thing enforcement is tested against, so the two paths share one allowance rather than gaining a second. Three smaller findings came with it. **`create or replace` on a function whose argument list changes creates a *second* function**, leaving the old arity to keep serving PostgREST — both had to be dropped, and grants re-issued, because a grant belongs to a signature. **A spec can ask for two things that cannot both be true**: §31 wanted two streams multiplexed into one response *and* an independent stop per column, and one response carries one `request.signal`, so the stop would have hidden a generation the provider kept billing — the documents were corrected rather than the contradiction worked around. And the browser caught what reasoning had not: the column rendered its error *instead of* its answer, so a generation failing at 90% would have discarded all of it — the rule `architecture.md` already states for the thread, quietly broken in a new surface, and visible the moment a real provider returned 402 mid-run. (F31)
9. **A test that cannot fail and a guard that cannot fire are the same defect, and F30 shipped both before catching either.** The catalog F14 built set `supportsImages` and `supportsPdf` true on every entry, so feature 30's whole subject — a disabled attach button, a warning, a server refusal — had nothing in the product that could reach it. Worse, the *tests* could not distinguish the two flags either: swapping them inside `acceptedMimeTypes()` left all 24 green, because with every entry setting both alike there was no case where the answer differed. The mutation was run before the code was believed, which is the only reason this was found rather than shipped — F15's lesson about a test comparing a function against itself, arriving through data instead of through logic. The fix was not a cleverer test but two more catalog entries, chosen because they are *different from each other*: one that reads nothing and one that reads images but not PDFs. With those the same mutation turns a test red, the tooltip has something to explain, and the dialog has one file to name instead of two. Both were listed from OpenRouter's `input_modalities` and then proven by real sends, per the catalog's own standard — and a test now pins that at least one entry accepts nothing, so a future tidy-up cannot quietly return the feature to being decorative. Two smaller measured findings: **a `disabled` button fires no pointer events**, so a Radix tooltip on one never opens and the explanation for the disabled state would have been the single unreachable thing on screen (`aria-disabled` instead); and **a literal space between a JSX expression and its following text did not survive to the DOM** — "DeepSeek V4 Flashcan't read files" — found by reading `textContent` in the browser rather than the source, which showed the space plainly. (F30)
10. **A `setState` updater that does anything is a bug React only shows you in development, and the screen never mentions it.** F29's composer started each upload inside the updater that added its chip — the natural place, since that is where the accepted files are computed. StrictMode double-invokes updaters in development, so **every attachment uploaded twice**: two rows, six storage objects, two confirm calls, and whichever finished last won the chip while the other leaked to the reaper for a day. Nothing on screen differed by a pixel; the chips, the progress and the send all behaved. What found it was reading `attachments` after a two-file test and counting four rows — the F19 rule again, verify on the surface the code writes to rather than the one that shows the outcome, and the third time this project has been caught by it. The fix is not a cleverer updater but the ordinary rule restated: updaters are pure, side effects live in an effect, and the effect carries a `started` set so a double-invoked *effect* cannot double-send either. The same audit then found `remove()` and `clear()` doing the same thing — revoking object URLs and issuing DELETEs inside their updaters — so the fix was applied three times, not once. Two smaller findings came with it, both from reading the installed SDK rather than the docs: `sendMessage({messageId})` is strictly a **replace** primitive that throws on an unknown id and truncates the thread after it, so minting an id for a new message means passing a whole message object instead; and a comment can be a defect in its own right — the hook's catch block *claimed* it deleted the failed row and never did, which was true only after `uploadAttachment` was made to clean up what it had created. (F29)
