# Progress Tracker

> **Role:** Live build status — what's done, in progress, and next.
> **Read at the start of every session**; **update after every completed feature.**
> **Relates to:** mirrors `build-plan.md` exactly; evicts old decisions to `constraints.md`.

Any AI agent reading this should immediately know what is done, what is in
progress, and what is next.

## How this file is maintained

- **Current Status is overwritten, never appended.** It holds three lines describing only the latest state. Do not keep previous statuses here — the record of what happened lives in `build-journal.md`.
- **Progress checkboxes are edited in place** — tick the box for the completed feature. Never restate, duplicate, or re-list the checklist.
- **Key Decisions holds the 10 most recent decisions, newest first.** When adding an 11th, file the oldest bullet under its topic in `constraints.md`, so this section never exceeds 10. Eviction is a move, never a delete — an old decision can still bind.

## Key Decisions

1. **A policy is scoped to a role, so "public" and "signed out" are not the same thing — and the gap between them is invisible until the wrong person opens the link.** F03's share policies are `for select to anon`, written a whole phase before anything rendered a shared conversation, and they are correct. What nobody had reason to notice is that Postgres applies a policy only when the *current role* matches, and Supabase resolves a signed-in JWT to `authenticated` — so reading a share link through the ordinary cookie-bound client returns **nothing** for any visitor who happens to be logged in. That is not an edge case; it is the common one, since a link is usually passed between two people who both use the product. Nothing errors: the query succeeds and comes back empty, and the page 404s as though the slug were wrong. Found by reading `pg_policies` while planning rather than by hitting it, which is the only cheap way it *could* have been found. The fix is a genuinely anonymous client, and the reason it is the fix rather than the alternative is worth keeping: **widening the policies to `to anon, authenticated` would have leaked far more than it solved**, because `listConversations()` deliberately carries no `user_id` filter — RLS is the boundary, not the query — so an `authenticated` policy of `using (share_slug is not null)` would put every shared conversation in the system into every user's sidebar. An isolation test now asserts the gap in both directions, so the next person to "simplify" this is told why it does not work. Two more from the same feature. **A test can pass every assertion and still be blind to the thing that matters**: the slug's uniqueness, length and character-set tests all stay green when `& 63` becomes `& 15`, which cuts the keyspace from 71 bits to 48 — only a test that samples which characters are actually emitted catches it, at `expected 16 to be greater than 60`. And **the dev server lies about `Cache-Control`**: it reports `no-cache, must-revalidate` where production sends the required `private, no-store`, so an invariant about caching verified in dev gives the wrong answer and invites a fix to something that was never broken. (F33)
2. **An invariant is a rule with a reason, and the honest move when a feature meets its edge is to name the exception and its cost — not to quietly break it, and not to let it veto the feature.** F32 had to write an assistant message the server never produced, because F31 persists nothing and the answer the user chose exists only in their browser. The rule it meets — history never comes from the request body — was written to stop a client steering a *completion* with a fabricated past, and the promote route calls no provider at all, so nothing about it can be steered. Two alternatives were available and both were worse: keeping every comparison server-side in memory (lost on deploy, broken by a second instance, and a "persists nothing" route quietly becoming stateful), or regenerating on promotion, which hands back a different answer than the one that was picked and defeats the feature it implements. So `architecture.md` names the route as its one exception and states the price in the same sentence — a crafted body can store a turn no model said, and F33 will publish it — with the corollary that any *other* route growing a field like this is a bug. **The second decision was the one that could have gone wrong silently**, and it is arithmetic rather than policy: the promoted row is written `used_shared_key: false` even though the shared key really did produce it, because F31 already counted that spend in `compare_count`. Marking it true counts one generation twice, and since the sweep only ever *lowers*, the raised floor blocks a legitimate refund on some *unrelated* orphaned slot later the same day — the user charged for a generation they never received, ten minutes after the fact. Nothing on screen would ever say so; the mutation is what says so, turning the new test red at `expected 2 to be 1`. Two smaller ones. **A `finally` block undoes a deliberate exception** — the promote hook leaves its pending flag true on success on purpose, so the button does not flash back for a frame before the navigation, which means every failing path has to clear it by hand and forgetting one leaves a permanently disabled button. And **the strongest verification was not a query but a question**: asking the promoted conversation "which of those three is the largest" and being told "the Blue Whale" proves the two rows are real history, which counting rows never could. (F32)
3. **A limit is only enforced where something can still see the evidence, and a feature that persists nothing is invisible to the job that reconciles it.** `reconcile_shared_key_usage()` has been correct since F02 for one reason nobody had to state: every spent shared-key slot left a `messages` row, so counting those rows and lowering `message_count` to match could only ever release orphans. F31's compare view spends the key twice per click and writes nothing at all — so **every slot it claimed would have come back within ten minutes**, and the daily cap would simply not have applied to `/compare`: two generations a click, unbounded, with only the global monthly breaker in the way. Nothing fails, nothing logs, and the only symptom is a counter that is lower later. It was found by reading the sweep during planning and asking what its source of truth actually was, which is the only way it *could* have been found; no test of the compare view would have noticed, because the sweep runs ten minutes after the test ends. The fix is a second counter moved inside the same atomic upsert that claims the slot, added to the sweep's `actual` — `message_count` stays the only thing enforcement is tested against, so the two paths share one allowance rather than gaining a second. Three smaller findings came with it. **`create or replace` on a function whose argument list changes creates a *second* function**, leaving the old arity to keep serving PostgREST — both had to be dropped, and grants re-issued, because a grant belongs to a signature. **A spec can ask for two things that cannot both be true**: §31 wanted two streams multiplexed into one response *and* an independent stop per column, and one response carries one `request.signal`, so the stop would have hidden a generation the provider kept billing — the documents were corrected rather than the contradiction worked around. And the browser caught what reasoning had not: the column rendered its error *instead of* its answer, so a generation failing at 90% would have discarded all of it — the rule `architecture.md` already states for the thread, quietly broken in a new surface, and visible the moment a real provider returned 402 mid-run. (F31)
4. **A test that cannot fail and a guard that cannot fire are the same defect, and F30 shipped both before catching either.** The catalog F14 built set `supportsImages` and `supportsPdf` true on every entry, so feature 30's whole subject — a disabled attach button, a warning, a server refusal — had nothing in the product that could reach it. Worse, the *tests* could not distinguish the two flags either: swapping them inside `acceptedMimeTypes()` left all 24 green, because with every entry setting both alike there was no case where the answer differed. The mutation was run before the code was believed, which is the only reason this was found rather than shipped — F15's lesson about a test comparing a function against itself, arriving through data instead of through logic. The fix was not a cleverer test but two more catalog entries, chosen because they are *different from each other*: one that reads nothing and one that reads images but not PDFs. With those the same mutation turns a test red, the tooltip has something to explain, and the dialog has one file to name instead of two. Both were listed from OpenRouter's `input_modalities` and then proven by real sends, per the catalog's own standard — and a test now pins that at least one entry accepts nothing, so a future tidy-up cannot quietly return the feature to being decorative. Two smaller measured findings: **a `disabled` button fires no pointer events**, so a Radix tooltip on one never opens and the explanation for the disabled state would have been the single unreachable thing on screen (`aria-disabled` instead); and **a literal space between a JSX expression and its following text did not survive to the DOM** — "DeepSeek V4 Flashcan't read files" — found by reading `textContent` in the browser rather than the source, which showed the space plainly. (F30)
5. **A `setState` updater that does anything is a bug React only shows you in development, and the screen never mentions it.** F29's composer started each upload inside the updater that added its chip — the natural place, since that is where the accepted files are computed. StrictMode double-invokes updaters in development, so **every attachment uploaded twice**: two rows, six storage objects, two confirm calls, and whichever finished last won the chip while the other leaked to the reaper for a day. Nothing on screen differed by a pixel; the chips, the progress and the send all behaved. What found it was reading `attachments` after a two-file test and counting four rows — the F19 rule again, verify on the surface the code writes to rather than the one that shows the outcome, and the third time this project has been caught by it. The fix is not a cleverer updater but the ordinary rule restated: updaters are pure, side effects live in an effect, and the effect carries a `started` set so a double-invoked *effect* cannot double-send either. The same audit then found `remove()` and `clear()` doing the same thing — revoking object URLs and issuing DELETEs inside their updaters — so the fix was applied three times, not once. Two smaller findings came with it, both from reading the installed SDK rather than the docs: `sendMessage({messageId})` is strictly a **replace** primitive that throws on an unknown id and truncates the thread after it, so minting an id for a new message means passing a whole message object instead; and a comment can be a defect in its own right — the hook's catch block *claimed* it deleted the failed row and never did, which was true only after `uploadAttachment` was made to clean up what it had created. (F29)
6. **A guard that has never had anything to refuse is indistinguishable from no guard, and F28 found three of them in one feature.** The `attachments` bucket had carried null `file_size_limit` and null `allowed_mime_types` since F03 — so every upload succeeded, and F03's own isolation fixture uploaded a text blob quite happily. Setting the limits turned that fixture red with `mime type application/octet-stream is not supported`, which is not a regression but the first evidence the limit exists; the fixture moved to a PNG and the limit stayed. The same shape twice more. The platform's `verify_jwt` flag looks like authorisation for an Edge Function and checks only that a JWT was signed by this project — so **any signed-in user** could have invoked a function whose entire job is deleting things; it is off, and the function proves the caller holds a service-role key by reading `shared_key_budget`, which F02 left policy-less precisely so that only a BYPASSRLS key can see it. And `reap_attachments_tick()` had been scheduled and green every hour since F02 while returning early on two absent Vault secrets — the F02 lesson about 866 green runs that corrected nothing, arriving again in a different costume. What separates a real guard from a decorative one is giving it something to refuse and watching it refuse: an 11 MB upload and an SVG through real signed URLs, a user JWT at the function, a seeded orphan row and a cascade-orphaned object with no row at all. The mutation that mattered most was the ordering one, and it is the one that would never have shown on screen — moving the attachment check below the "will reach a provider" line returned the **identical** `400 attachment_not_ready` and left behind a new "New chat" holding a prompt with no answer, plus a shared-key slot claimed by an early return that skipped the refund. Same status, same body, same code, different database. (F28)
7. **A capability built for one caller quietly encodes that caller's assumptions, and the second caller is what exposes them.** F18 gave messages scroll anchors and a jump highlight, and both worked perfectly for two features — because the only thing jumping was the outline rail, which lists *prompts*. F27 pointed search at the same machinery and found it half-built: `AssistantMessage` had no anchor at all, so half of every result set would have navigated to the right conversation and left the reader at the top of a sixty-message thread with nothing marking the match; and `isHighlighted` was never passed to it either, so even landing correctly said nothing about which message was meant. Neither was a bug in F18 — its own caller never needed them — and neither failed any test, because the gap is an absence rather than a fault. What found them was reading the code the new caller would use *before* wiring it up, and asking what a result pointing at an answer would actually do. The fix carried its own lesson: the obvious move was to copy `UserMessage`'s `border-primary`, and DESIGN.md forbids it outright — `message-assistant` says a response carries no fill and no border, "the content, not a card" — so the highlight became the 2px left indicator `outline-rail-item` already uses, with a transparent border always present so highlighting cannot reflow the thread. **Reusing a mechanism means auditing it against the new caller's cases, not just calling it**; and when a component refuses the obvious styling, the design system usually already names what to do instead. Third time in three features that a browser locator collided under strict mode — the habit that works is refs from `snapshot`, not hand-composed CSS. (F27)
8. **A test can be green because something *else* is protecting the thing it claims to test — and the mutation that shows you is not the one you predicted.** F26's isolation test asserted that a search never returns another user's message. Weakening the `messages` owner policy to `using (true)` left the entire suite green, because `search_messages` inner-joins `conversations` and *that* table's policy hides the row instead: either policy alone is sufficient, so no test of this query can single out either one. Real defence in depth, and a comment claiming the messages policy was "the only thing scoping this" that was simply false. Weakening **both** then turned exactly one test red, and it was the wrong one — *"finds nothing for a user with no messages"*, not the isolation test, which still could not fail. Its assertion searched the *snippet* for the stranger's wording, and `ts_headline` returns a **fragment**: the opening words of a short message are routinely cut, so the substring was absent whether or not the row was present. Rewritten to assert on `conversation_title`, which comes off the row rather than out of the headline, the same mutation turns two tests red. Three rules. **A green suite under a broken guard means the guard you broke was not the one doing the work** — find out which one is, and say so, rather than assuming the nearest one. **Never assert on a value the database is free to reformat**: a snippet, a headline, a rendered date and a truncated preview are all derived, and an assertion against one of them fails to fail. And the F03 habit needs a corollary now that policies are being weakened on a *live* project — restore in the very next call and verify with `pg_get_expr`, never at the end of a batch of experiments. Separately, and cheaply learned: a `rollback` inside an `execute_sql` batch rolls back the whole batch, including the insert before the explicit `begin`, which made a seeded row vanish and read as a broken index. (F26)
9. **The second half of a library's focus behaviour is the half that runs after yours.** F24 found that Radix never calls `onOpenChange` for a parent-driven open; F25 found the mirror image one layer along, in the same primitive family. Inserting a prompt worked on the first try — right body, right caret, panel closed — and focus was sitting on the trigger button rather than in the textarea, because Radix restores focus to the trigger when a popover closes and does it *after* the `requestAnimationFrame` the composer used to place its own caret. Both calls ran; the last one won; nothing anywhere reported a problem. `onCloseAutoFocus` is the seam, which is the third time this project has ended up there — F21 used it for the rename input and the constraint has said since then that a Radix menu traps focus until it has finished closing. What is new is that the yield had to be **conditional**: preventing the restore unconditionally would fix insertion and break Escape, leaving a keyboard user who changed their mind on `<body>` with nothing to tab from. So the flag says *why* the panel is closing, and only the path with somewhere better to send focus takes it. Two rules. **When a library and your code both move focus, the question is not whether yours runs but whether it runs last** — and the way to find out is to read `document.activeElement` after the interaction rather than to look at the screen, which showed the correct text in the correct place throughout. And **a fix that changes a shared exit path has to be checked on every way in**: insert, Escape, and click-outside are three closes, and the first version was right about one of them. The same session repeated F24's harness mistake despite having written it down — a suppressed `strict mode violation` on an ambiguous "New chat" locator read as a broken feature for several minutes, in a sidebar that contains both a New chat button and a conversation named "New chat". (F25)
10. **A library only calls the handler for the changes *it* initiates, and the one it never calls for is the one the component was counting on.** `PromptDialog` seeded its fields inside `onOpenChange`, copied from F23's `SystemPromptControl`, where it is correct — that dialog owns its own trigger, so every open *is* Radix-initiated. This one is opened by a parent flipping the `open` prop, and Radix does not call `onOpenChange` for that. The handler therefore ran on every close and on no open at all. Nothing failed: typecheck, lint and 320 tests stayed green, and the symptom only appears on the *second* use in one page session — "New prompt" opened holding the previously saved prompt, and saving wrote a byte-for-byte duplicate, same title, same body, same tags. The fix is not a better handler but the removal of the need for one: the library mounts the dialog only while it is open, so `useState` initialisers do the seeding and it cannot be skipped. The remount is observable — `useId` returns a new value per open, which broke a hardcoded selector mid-session and was the confirmation. Two rules this leaves. **A pattern copied from a working component carries the conditions that made it work**, and "who initiates the state change" is one nobody writes down: F23's seeding, F21's `onCloseAutoFocus`, and F18's publish effect are all correct in their own component and none of them transplants unexamined. And **prefer the arrangement that makes the mistake unrepresentable** over the one that requires an event to fire — the same move as F16's atomic claim and F10's `sharedTitleModel()` taking no user id. Two harness lessons came with it, both self-inflicted: suppressing stderr on `playwright-cli fill` hid a `strict mode violation` and turned a silently-failed fill into several minutes of hunting a data bug that did not exist. (F24)
